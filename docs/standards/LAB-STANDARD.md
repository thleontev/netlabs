# NetLabs — стандарт лабораторных работ

## 1. Область применения

Стандарт обязателен для **новых** EVE-NG/GNS3 лабораторий. Для старых GNS3-проектов применяется постепенно и без изменения содержимого. Режимы агента и границы изменений определены в [AGENTS.md](../../AGENTS.md). Это учебный репозиторий: не требуется превращать каждую лабораторию в отдельный программный пакет.

## 2. Навигация

**README репозитория**: две одинаково оформленные таблицы EVE-NG/GNS3 («Раздел | Лаборатории | Что изучается»), единый быстрый старт, политика образов.

**README категории**: краткое назначение категории, таблица лабораторий («Лаборатория | Содержание | Статус»), ссылка на импорт и рекомендуемую топологию. Допустим дополнительный уровень протокола (eve-ng/IGP/OSPF/). Не вставлять сюда полную архитектуру лаборатории.

**README лаборатории** — порядок разделов:
1. Назначение, учебные цели и уровень фактической проверки.
2. Топология: одно PNG-превью с ссылкой на SVG, если SVG существует.
3. Архитектура: роли, underlay/overlay, control plane/data plane, протоколы, границы модели.
4. Состав и требования: тип/версия образов, память, узлы, известные ограничения.
5. Таблица файлов с назначением каждого варианта проекта и стадии.
6. Быстрый старт с относительной ссылкой на IMPORT-RU.md (либо встроенной инструкцией для простого проекта).
7. Проверки: команды и **ожидаемые**, не выдуманные результаты.
8. Упражнения/сценарии и ссылки.
9. Ограничения и подтверждённый уровень L1–L4.

Без «истории изменений», маркетинговых описаний и повторения полного содержания дополнительных документов.

## 3. Структура новой лаборатории

~~~text
<LAB-NAME>/
├── README.md
├── IMPORT-RU.md             # для EVE-NG; допустимо заменить разделом для простых GNS3
├── <LAB-NAME>.unl            # либо .gns3
├── configs/
│   ├── R1.cfg
│   └── R2.cfg
├── docs/
│   ├── topology.svg         # если есть редактируемый источник
│   ├── topology.png
│   ├── EXERCISES.md
│   └── DIAGNOSTICS.md
├── scenarios/
│   ├── 00-BASELINE.md
│   └── 01-LINK-FAILURE.md
└── tools/                   # только при необходимости
~~~

Названия проекта и каталогов должны быть осмысленными и стабильными. Не создавать пустые файлы и каталоги ради соответствия дереву. Если топология документирует разные варианты — дать каждому варианту понятное имя. Не дублировать схемы в корне и docs без необходимости.

Для лабораторий со стадиями использовать configs/00-*, configs/01-*, ... . В README явно указывать соответствие стадии, исходных .cfg и варианта .unl; полный конфиг нельзя без очистки накладывать поверх другой стадии, если это не предусмотрено.

## 4. Содержимое и подтверждение

- Объяснить назначение каждого сетевого элемента; указать физические линки, IP/маски, VLAN/VRF/VNI/AS/area только там, где они реально заданы в конфигурациях.
- Команды отличаются по IOSv/IOS XRv/NX-OSv/VPCS/Linux; не смешивать синтаксис.
- Для EVE-NG указать имя/тип QEMU-образа **из проекта**, что импортирует .unl, что приходится настраивать вручную и как проверить Startup-configs. Если требуется Wipe, предупредить о потере NVRAM/дискового состояния.
- Для GNS3 указать, существует ли .gns3; для архива только из .txt/.png не заявлять о готовом проекте.
- Для каждого упражнения: действие, наблюдение, команда проверки и критерий успешности. В отказных сценариях обязательны baseline, rollback и проверка возврата.
- Использовать термины «модель» и «имитация» для частей, которые не реализуют реальные сервисы (например, ACL вместо stateful DDoS scrubbing или firewall).
- Примеры адресов: предпочтительно RFC 5737 (192.0.2.0/24, 198.51.100.0/24, 203.0.113.0/24) и тестовые/частные диапазоны, если функциональность допускает.

## 5. Статус лаборатории

| Уровень | Название | Доказательство |
|---|---|---|
| L1 | Structure | Файлы, навигация, читаемая схема |
| L2 | Static validated | XML/JSON, ID, ссылки и startup-config проверены статически |
| L3 | Runtime verified | Реальный запуск на названном образе, подтверждённая связность и соседства |
| L4 | Scenarios verified | Подтверждены неисправности, диагностика и rollback |

Не подменять L3 тестом XML. Если общий валидатор выдаёт предупреждения, объяснить, почему они допустимы. Если отсутствует доступ к EVE-NG/GNS3 — указать «L3/L4 не проверялись».

## 6. Контроль качества

**Базовая команда:** python3 tools/validate_netlabs.py --lab "eve-ng/MPLS/MPLS Service Provider Advanced"

**Проверка всех файлов:** python3 tools/validate_netlabs.py --all

**Автотесты валидатора:** python3 -m unittest discover -s tests -v

Валидатор не запускает виртуальные устройства. Он сообщает ERROR об ошибках структуры, WARN о документации и неоднозначном соответствии .cfg; флаги --strict-docs и --strict-configs повышают соответствующие предупреждения до ошибок. Для стадий, преобразований startup-config и специфики платформ всегда запускать локальные lab/tools/*validate* либо *check*; общий валидатор не заменяет их. Ни один скрипт проверки не должен автоматически исправлять .unl/.cfg.
