# 08 — Firewall forwarding остановлен, VRF остаются изолированными

**Этап:** 03 + топология с FW  
**Задача:** проверить путь CLIENTS → LEAF-02 → Linux FW → LEAF-02 → APPS, включая обратные маршруты.

> Только изолированная лаборатория EVE-NG. Изменения применяются вручную к тестовым узлам. Команды не выполнять на рабочих сетевых устройствах. Конфигурации NX-OSv 9.3(x) и реальное поведение требуют проверки на образе.

## Baseline: докажи, что всё работает до сбоя

Настроить FW с корректными интерфейсами и nftables; на Linux `ip -br a`, `ip route`, `sysctl net.ipv4.ip_forward`, `nft list ruleset`. Убедиться, что разрешённый ICMP CLIENT-A→APP-C проходит, а запрещённый новый TCP — нет. LEAF-02: `show ip route vrf CLIENTS` и `show ip route vrf APPS`.

Перед изменением сохрани вывод `show running-config`, таблицы маршрутизации и результат теста. Фиксируй время и симптом, а не только успешность ping.

## Внести неисправность

На **FW-LINUX**:
```bash
sudo sysctl -w net.ipv4.ip_forward=0
```

## Найти причину — control plane и data plane

- BGP EVPN, OSPF и Type-5 на Nexus остаются; L2 traffic внутри одной VRF не должен пострадать.
- Разрешённый ранее inter-VRF ICMP теперь должен перестать проходить, поскольку FW перестал пересылать пакеты.
- На LEAF-02 статические маршруты через 172.31.10.2 / 172.31.20.2 остаются в VRF; `tcpdump -ni <client-if> icmp` и `tcpdump -ni <app-if> icmp` должны локализовать место остановки.
- Отдельно проверить обратный маршрут до 192.168.10.0/24 на FW и forwarding counters `nft list ruleset`.

## Откат

На FW-LINUX:
```bash
sudo sysctl -w net.ipv4.ip_forward=1
```
Если ОС ранее имела иное значение — вернуть его; persistent sysctl не менять. Проверить ICMP и блокировку TCP.
