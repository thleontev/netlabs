# NetLabs — инструкции для ИИ-агентов

Этот файл действует во всём репозитории. Перед работой прочитайте [стандарт лабораторий](standards/LAB-STANDARD.md), существующий README соответствующей категории и минимум одну близкую лабораторию.

## Назначение и приоритеты

NetLabs — библиотека учебных сетевых лабораторий EVE-NG и GNS3, а не программный фреймворк. Приоритеты: техническая корректность → воспроизводимость запуска → сохранность исходных проектов → ясная и компактная документация. Не создавайте инфраструктуру, зависимости и CI без практической необходимости.

## Режимы работы (определите до изменений)

1. **Documentation** — только Markdown, ссылки, схемы и каталогизация. Не изменяйте содержимое конфигураций, .unl, .gns3, UUID, адреса, интерфейсы, топологию и сетевую логику. Перемещение/переименование функциональных файлов — только по явному заданию.
2. **Implementation** — проектирование или функциональное изменение лаборатории. Сначала опишите ожидаемую топологию, платформы, этапы и критерии приёмки; затем создайте конфигурации, топологию и документацию. Сохраните рабочие исходные версии при миграции.
3. **Validation** — анализ только для чтения. Отчёт об ошибках и ограничениях; не исправляйте найденное без отдельного поручения.

Если режим явно не задан и пользователь просит «оформить», выбирайте Documentation. Не подменяйте оформление функциональной переработкой.

## Структура

- Корневой README: только назначение, навигация EVE-NG/GNS3, краткий старт. Таблицы платформ оформляйте одинаково: «Раздел | Лаборатории | Что изучается».
- README категории (например, eve-ng/MPLS/README.md): каталог независимых лабораторий, краткие описания и ссылки на быстрый старт. Не дублируйте полный README лаборатории.
- Независимая лаборатория: отдельная папка с README.md и файлом проекта; по потребности IMPORT-RU.md, configs/, docs/, scenarios/, tools/. Не добавляйте пустые каталоги.
- Для **новых** работ сетевые конфигурации храните в configs/<DEVICE>.cfg. Для этапов используйте configs/00-..., 01-..., 02-...; каждый этап содержит полный конфиг, а не неполный patch, если не указано иное.
- Старый архив GNS3 может содержать .txt, файлы без расширения и неполные проекты. Никакого массового переименования или реконструкции без подтверждённых исходных данных.
- Схемы: желательно редактируемый SVG плюс PNG-превью; существующие оригиналы не перерисовывать без необходимости. В README — одно превью, а не повторения одной схемы.

## Техническая целостность

- У EVE-NG **наличие configs/*.cfg само по себе не означает автозагрузку**. Для заявленного startup-config проверьте config="1", наличие корректной записи в objects/configs, соответствие node ID, Base64 и встроенного текста исходному конфигу с учётом документированного преобразования. Используйте существующие лабораторные скрипты проверки там, где они точнее общего валидатора.
- Для GNS3 проверьте JSON, node_id, endpoints связей и наличие необходимых внешних файлов; не обещайте автоматическую загрузку конфигураций без проверки механизма конкретного шаблона устройства.
- Не придумывайте команды и параметры образов. Проверяйте различия IOSv, IOS XRv, NX-OSv, IOSvL2, VPCS и Linux. Нельзя «нормализовать» синтаксис между платформами.
- Не включайте в git образы устройств, секреты, дампы живых сетей или их эксплуатационные данные. Для примеров применяйте учебные адреса/ASN; без подключения к реальным сетям.
- Аварийные сценарии должны содержать baseline → инъекцию одной неисправности → наблюдения → диагностику → rollback → повторную проверку. Явно предупреждайте об изолированном стенде.

## Доказательства и качество

- Уровни: **L1 Structure** (структура), **L2 Static validated** (проверка файлов), **L3 Runtime verified** (запуск и протоколы), **L4 Scenarios verified** (проверенные отказные сценарии). Никогда не повышайте статус до L3/L4 без фактического стендового подтверждения.
- Отличайте «ожидается» от «проверено». Не выдумывайте результаты ping, BGP Established, задержки сходимости или MTU.
- В README не ведите историю изменений: её хранит Git. Пишите по-русски, технические обозначения CLI оставляйте оригинальными. Ссылки должны быть относительными и рабочими.
- После изменений запустите: python3 .agents/tools/validate_netlabs.py --lab "путь/к/лаборатории". Для EVE-NG также применяйте специальные проверки из tools/ конкретной лаборатории. Если статическая проверка не выполнялась, обязательно укажите это.
- Для новой лаборатории используйте [шаблоны](templates/) и [правила](standards/LAB-STANDARD.md), а для повторяемых задач — skills: [create](skills/netlab-create/SKILL.md), [document](skills/netlab-document/SKILL.md), [validate](skills/netlab-validate/SKILL.md), [migrate](skills/netlab-migrate/SKILL.md).

## Изменения через Git

Не изменяйте работающие лаборатории ради внедрения стандартов. Перед коммитом проверьте git diff, отсутствие неожиданных изменений .cfg/.unl/.gns3, результат тестов и ссылки. Кратко перечислите созданные файлы, проверки, что не проверено, известные предупреждения и ссылку на PR. Не сливайте PR самостоятельно, если об этом не попросили.
