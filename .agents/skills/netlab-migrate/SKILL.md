# Привести старую лабораторию к стандарту

## Основное правило

Миграция структуры — не рефакторинг сети. Архив GNS3 часто состоит из .txt/.png и может не иметь .gns3. Сохранять оригиналы и их связь с проектом; не генерировать фиктивную топологию из догадок.

## Процедура

1. Выявить все оригинальные файлы, расширения, варианты топологии, сохранённые проекты и внешние зависимости.
2. Зафиксировать исходные пути и контрольные суммы функциональных файлов. Определить, что можно безопасно переименовать/переместить, а что должно остаться без изменений.
3. Добавить README по шаблону, указать честный статус: проект .gns3 есть или отсутствует; конфигурации загружаются автоматически или вручную; фактические образы неизвестны или указаны в проекте.
4. Если пользователь разрешил реструктуризацию — переносить только необходимое, обновить относительные ссылки; при изменении внутренних путей .gns3 убедиться, что проект остаётся валидным, иначе оставить исходные пути.
5. Для .txt/.cfg: не менять содержимое, расширение и имя без отдельной причины/разрешения. Для отсутствующих данных не создавать пустые конфиги.
6. Проверить diff, контрольные суммы и python3 tools/validate_netlabs.py --lab "путь"; сравнить число узлов/линков до/после.
7. Перечислить перенесённые и нетронутые файлы, обнаруженные пробелы, статус проверок и неизвестные параметры. Без реально запущенного GNS3 не заявлять совместимость L3/L4.

## Не делать

Не удалять архивные варианты, не переписывать их как новый EVE-NG проект без прямого запроса, не добавлять ненужные CI workflow, генераторы и машинные метаданные.
